H1 · Aurora continuity

What happens when Aurora's Pod disappears mid-reply?

The same visible event requires two different recovery strategies.
CLASSIFY THE FAILURE BEFORE CHOOSING THE RECOVERY05 / 19
Team Member 1, 30-40 sec.
Aurora is sending multiple bubbles through one long-lived SSE connection. When Pod A disappears, the first engineering question is not which Kubernetes object we used. It is whether the process was warned. Planned replacement creates a drain window. Sudden crash does not. That classification drives the next two slides.

H1 · Planned replacement

Stop new work first; finish the active stream before exit

Readiness stops new traffic. It never migrates an existing SSE connection.
GRACEFUL DRAIN · CURRENT STREAM FINISHES ON THE OLD POD06 / 19
Team Member 1, 50-60 sec.
Reveal the five-step causal chain. SIGTERM begins termination. Readiness removes the Pod from new Service traffic. Existing SSE connections are not transferred anywhere; they stay on the old Pod. preStop, the termination grace period and JVM graceful shutdown let the current stream finish. Messages and terminal state are persisted, while the Deployment restores replica capacity independently.

H1 · Sudden crash

A broken stream must still reach a clear ending

Reliability does not mean every stream survives. It means every action reaches a clear outcome.
APPLICATION-LEVEL RECONCILIATION · NO FABRICATED CONTINUATION07 / 19
Team Member 1, 60-75 sec.
A real SIGKILL bypasses every graceful mechanism. The socket and executor disappear, but the authoritative turn may still say GENERATING. That mismatch creates an orphan. ConversationTurnRecoveryJob scans stale non-terminal turns, detects the orphan and reconciles it to INTERRUPTED. Kubernetes can replace capacity; only application logic can decide what the unfinished conversation means.

H2 · Shared state

PostgreSQL preserves truth, not every live interaction

Shared short-lived state needs a shared address, not a persistent volume.
STATE OUTSIDE PODS · REPLICA-INDEPENDENT INTERACTION08 / 19
Team Member 2, 55-65 sec.
Continue from H1. PostgreSQL already protects the durable timeline, but a multi-Pod API still has shared short-lived state. Build the failure: login reaches Pod A and the session exists only in that process; the next request reaches Pod B and loses the interaction context. Moving sessions, streams, limits and scheduler locks to Redis makes every healthy API replica useful. This is not durable business truth; it is replica-independent coordination.

H2 · State architecture

Put each state where its failure semantics make sense

Durable truth and fast coordination are different reliability contracts.
POSTGRESQL IS AUTHORITATIVE · REDIS IS SHARED AND REBUILDABLE09 / 19
Team Member 2, 60-70 sec.
Reveal the replaceable Pods, then the two state tiers. PostgreSQL owns anything whose correctness must survive until tomorrow: turns, timeline, outbox, receipts and projections. Redis owns short state that must be shared now but can be rebuilt or reacquired. Replace a Pod and neither tier changes. Restart Redis and users may re-authenticate or live streams may rebuild, while PostgreSQL remains authoritative. Our kind-full and Academy profiles intentionally run Redis without persistence.

Which signal should decide the number of Workers?

OUR PROBLEMFixed Workers either leave memory work waiting or sit idle.
KEDA supplies the missing input. HPA remains the controller that changes replicas.
CPU ANSWERS RESOURCE USE · OUTBOX PRESSURE ANSWERS USER DELAY10 / 19
Team Member 2, 60-70 sec.
Begin with the definition and the reason, then clear both frames. A Worker often waits on the AI provider or PostgreSQL, so CPU may remain near two percent while post-conversation work accumulates. Each click is one causal step. The API writes an outbox row in the same transaction. Ready count or oldest age crosses a threshold. H3 · OpenTelemetry

One Trace ID joins eight operations into one journey

Trace = journey. Span = operation. IDs connect what happened, where and because of what.
TRACE · SPAN · TRACE ID · SPAN ID · 8 MEASURED SPANS12 / 19
Team Member 3, 60-70 sec.
Teach the vocabulary inside a real-looking trace, not below it. A trace is the complete causal journey. Each bar is a span: one named operation with a start, duration and status. All eight spans share one Trace ID. Every bar has its own Span ID, and a child records the parent Span ID that caused it. OpenTelemetry creates and transports this structure; Jaeger lets us inspect it.

H3 · W3C Trace Context

Causality must survive after the HTTP request ends

The outbox carries causal context across time and process boundaries.
TRANSACTIONAL OUTBOX · TRACEPARENT · REMOTE PARENT · CONSUMER SPAN13 / 19
Team Member 3, 65-75 sec + Jaeger demo.
The HTTP request ends before the Worker begins. We persist W3C traceparent in the same outbox row as the business event. The Worker extracts it and starts a CONSUMER span with the API secured-request Span ID as its remote parent. Memory and profile projections become children of that consumer. We verified the exact parent Span ID, not merely a shared Trace ID.

H3 · Privacy-aware observability

The conversation must never become telemetry

Export operational meaning. Never export the person behind it.
APPLICATION ALLOWLIST → COLLECTOR REDACTION → PRIVACY-SAFE TRACE14 / 19
Team Member 3, 60-70 sec + attribute inspection.
Aurora conversations are private, but turning telemetry off would make asynchronous failures impossible to explain. We therefore constrain the schema. The application emits bounded operational attributes; it never emits conversation text, prompts, completions, stable user identifiers, request bodies or full SQL. The Collector removes sensitive attributes again before export. The live scan found zero forbidden keys while keeping eight spans useful.

04 · Controlled change

A safe revision must pass two different gates

Policy controls execution. Progressive delivery controls exposure.
KYVERNO · ADMISSION CONTROL → ARGO ROLLOUTS · PROGRESSIVE DELIVERY15 / 19
Main speaker, 40-50 sec.
A revision must answer two different questions. Kyverno evaluates declared workload intent before a Pod exists. Passing that gate does not mean the behavior deserves full exposure. Argo Rollouts then limits who sees the candidate and uses readiness or analysis to promote or abort it. Advanced AI revisions may change code, configuration, routing and prompt policy together, so both gates matter.

Controlled change · Kyverno admission

Unsafe intent stops at the API boundary, not after deployment

A manifest is an intention. Admission is the first executable proof.
KYVERNO · REAL ALLOW + REAL REJECTION + KILL SWITCH16 / 19
Main speaker, 45-55 sec.
Three unsafe intentions approach the admission boundary: root execution, missing resource bounds and a mutable image tag. Kyverno rejects each before the scheduler can create a Pod. A compliant workload passes. We also removed and restored the policy to verify the operational kill switch. This is admission-time enforcement; it is not a claim about auditing workloads that already existed.

Controlled change · Argo Rollouts

Configured canary weight does not guarantee real traffic

Rollout weight proposes exposure. Readiness and endpoints determine eligibility.
ARGO ROLLOUTS · LIMIT BLAST RADIUS · PROMOTE OR ABORT17 / 19
Main speaker, 50-60 sec.
The verified local mechanism expressed setWeight as ReplicaSet ratio behind one Service. Three stable Pods and one candidate represent 25 percent configured weight. But the candidate fails readiness, so it never enters Service endpoints and receives zero real traffic. Argo aborts the revision and stable capacity remains available. Weight is intent; endpoint eligibility is operational fact.

05 · Synthesis

A green cluster is only the innermost layer of AI reliability

Kubernetes keeps resources healthy. The application must prove that meaning survived.
RESOURCE → SEMANTIC → EXPERIENCE RELIABILITY18 / 19
Main speaker, 55-65 sec.
Build outward. Kubernetes gives resource reliability: running Pods, replicas and eligible endpoints. Advanced AI adds semantic objects the platform cannot interpret: a turn, a memory projection, an identity version and a causal journey. The outer objective is experience reliability: continuity, timely memory, authorized identity and consented connection. A green cluster is necessary, but it is only the innermost ring.

The takeaway

Advanced AI is not a model behind an endpoint.
It is a process that persists through time.
