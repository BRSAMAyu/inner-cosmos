Capability 1 · Runtime ContinuityTeam member 1 · 75 sec

Graceful termination and SIGKILL have different outcomes

Graceful Pod termination
COMPLETED
  • 2 of 2 bubbles committed
  • 0 duplicated messages
  • 0 content loss
Direct JVM SIGKILL
INTERRUPTED
  • Active stream cannot continue
  • RecoveryJob reaches a terminal state in ~22 s
  • Reconnect returns it in 1.62 s
Validated on local kind with real PostgreSQL and Redis. Hard failure recovery prevents a silent two-minute hang; it does not resume the interrupted generation.
Be precise: the SIGKILL path is not seamless streaming. The improvement is explicit terminal recovery rather than a permanent PLANNED turn and silent client suspension.

05 · Engineering LessonsMain speaker · 90 sec

What the project changed in our understanding

01
Infrastructure recovery and application recovery are different responsibilities.
A replacement Pod cannot decide whether an AI turn is complete.
02
Scaling signals should represent user-visible waiting.
Queue age describes unfinished product work more directly than API CPU.
03
Asynchronous work needs explicit causal-context propagation.
Per-service dashboards cannot reconstruct a cross-role result.
04
A platform component matters only when it protects a product invariant.
Success, failure and recovery must all be observable.
This is the advisor-facing conclusion. The project taught the team how application invariants become recovery ownership, scaling signals, trace structure and rollout controls.

Conclusion

Advanced AI systems need more than container orchestration.

They need application-aware continuity, workload-aware elasticity, causal observability and controlled change.

Final sentence: Kubernetes provides reliable generic control loops. Advanced AI systems must expose the application state and signals those loops need.
