Lesson 01 · Continuity

零损失不是 PDB 或 graceful shutdown 的单项能力，而是一个组合性质

Kubernetes 能替换 Pod，但不知道一次 Aurora turn 是否已完成。PostgreSQL 能保存 turn，但不会告诉客户端如何恢复。Last-Event-ID 能表达游标，但没有统一事件序列和 terminal event，客户端仍会悬挂。四者缺一即失效。

Lesson 03 · Work pressure

exactly-once 是端到端的业务效果，不是任何单一组件的开关

扩缩应该追踪用户等待，而不是机器忙碌——CPU 是资源现象，oldest age 是用户体验现象。KEDA 的价值不只是自动扩容，而是把用户可感知的等待翻译成控制信号。而让扩容安全的，是一套与扩缩正交的机制。

H3 · CAUSAL OBSERVABILITY

如果系统无法保留一次 AI 行为跨同步与异步边界的因果关系，我们就无法判断一次回复为什么慢、一条记忆为什么迟、一个主动回访为什么没有发生。

一对多 fan-out、批处理或跨长时间窗口的派生任务，才应使用 span link，以避免伪造同步调用树。

Lesson 04 · Causal observability

AI 系统最容易为了调试，把用户的一切都塞进 trace

因果必须保留，否则无法解释一条用户体验是怎样产生的；但正文、prompt、稳定标识一旦进入 label、trace attribute、高基数维度或日志，就再也收不回来。可解释与可泄露之间没有中间状态。

Lesson 02 · Semantic health

最危险的 AI 故障不返回 500

Prompt 退化、结构化输出解析率下降、Provider fallback 增多、TTFT 变慢、记忆召回相关性下降、安全输出质量退化——JVM、HTTP 与 liveness 全程绿灯。所以部署判断必须从「Pod 是否 Running」升级为「这个版本是否仍然维持用户体验和安全不变量」。

The point

故障演练的价值不是证明我们原来就是对的，而是设计一个足以推翻自己的实验

我们第一次执行 delete --force 后，实验「通过」了，SSE 完整结束。当时很容易直接写 PASS。
进一步检查才发现真正的硬故障根本没有发生——而当我们让它真正发生时，系统立刻暴露了一个我们原本不知道的 bug。

三条主动公开的边界
kill -9 时正在生成的那一次 turn 无法续流；保证的是约 22 秒内进入终态、重连不悬挂
Rollouts 的自动回滚由坏 readiness + progressDeadlineAbort 实证；AI 质量指标驱动的语义回滚尚未实证
KEDA 的积压是合成注入的（走真实 schema / worker / lease / inbox 路径）；Academy 可移植性单独声明

工程成熟度也体现在知道什么暂时不值得采用

DELIBERATELY NOT BUILT
没有为展示云原生把模块化单体强拆成微服务
没有为增加名词数量引入 Kafka / Dapr / Service Mesh / Knative
没有把同节点静态 PV 备份包装成跨区域灾备

一个组件只有同时具备产品连接、真实成功证据、失败证据、资源边界、kill switch 和环境 fallback，才值得进入主演示。

AI Agent 的云原生化，不是把模型服务装进 Pod
